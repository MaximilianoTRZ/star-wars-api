# ADR-002: Paginación propia y uniforme

## Estado

Aceptado

## Contexto

SWAPI no es uniforme:

- `/people?page=&limit=` pagina.
- `/films` devuelve todo sin paginar.
- Las búsquedas (`?name=`, `?title=`) devuelven una lista sin paginar.
- Una página fuera de rango devuelve la última página con 200, no una página vacía.

Si se expone esto tal cual, el consumidor de la API tiene que conocer cada caso.

## Decisión

Todos los listados devuelven el mismo `PageResponse<T>`: `content`, `page` (base 1), `size` (1–100), `totalElements` y `totalPages`. `CatalogService` elige la estrategia según los filtros:

| Caso | Cómo se pagina |
|---|---|
| Listado de un recurso que SWAPI pagina | Delegada en SWAPI; si `page > total_pages` → `content: []` |
| Films sin filtros | En memoria (`Paginator`) |
| Búsqueda por nombre o título | En memoria sobre el resultado |
| Filtro por ID (con o sin nombre) | Página de 0 o 1 elemento |

## Alternativas descartadas

- **Exponer la paginación de SWAPI:** obliga al cliente a manejar tres formatos distintos.
- **Traer siempre todo y paginar en memoria:** más simple, pero baja ~80 registros por request cuando SWAPI ya pagina.

## Consecuencias

- Un único contrato, fácil de documentar en OpenAPI y de consumir.
- `Paginator` es una clase pura, testeable sin Spring.
- La paginación en memoria se beneficia del caché de la Fase 2 (ADR-007).
