# ADR-013: Errores con Problem Details (RFC 9457)

## Estado

Aceptado

## Contexto

La API tiene errores de varios orígenes, y cada uno arma la respuesta en un lugar distinto:

- **Spring MVC:** parámetros inválidos, body ilegible, ruta inexistente, método no soportado.
- **Dominio:** recurso inexistente, SWAPI caída o con una respuesta inesperada.
- **Cadena de seguridad:** token ausente, inválido o sin scope. Estos errores corren antes de Spring MVC y no pasan por el `@RestControllerAdvice`.

Sin una decisión explícita, cada origen devuelve un formato distinto: el JSON del `/error` de Spring Boot, un 401 vacío de Spring Security, o mensajes armados a mano.

## Decisión

Todos los errores se devuelven en el formato **Problem Details for HTTP APIs**, definido en el [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457). Ese RFC reemplaza al [RFC 7807](https://www.rfc-editor.org/rfc/rfc7807), que es el nombre con el que se lo suele conocer, y mantiene el mismo formato.

- **Media type:** `application/problem+json`.
- **Campos estándar:** `type`, `title`, `status`, `detail`, `instance`.
- **Extensiones:** `timestamp` siempre; `requestId` desde la Fase 3; `errors: [{field, message}]` en los 400 de validación.
- **`type` estable** con la forma `/problems/{nombre}`. Es parte del contrato: el cliente decide por `type`, no por el texto de `detail`.

Implementación:

- `ProblemDetail` nativo de Spring Framework.
- `GlobalExceptionHandler` extiende `ResponseEntityExceptionHandler`, así los errores de Spring MVC ya salen en este formato.
- `ProblemDetailFactory` es el único lugar donde se arma un error. La usan el handler, el `AuthenticationEntryPoint` (401) y el `AccessDeniedHandler` (403).
- Los errores 5xx nunca exponen detalles internos: el stack trace va solo al log.
- OpenAPI documenta un único schema `ProblemDetail`, registrado desde un `OpenApiCustomizer`.

## Alternativas descartadas

- **JSON de error propio** (por ejemplo, `{code, message}`): no es un estándar, así que los clientes y las herramientas no lo reconocen, y hay que documentarlo desde cero.
- **El `/error` default de Spring Boot:** tiene otro formato, expone campos como `path` y `trace` según la configuración, y no cubre los 401/403 de la cadena de seguridad.
- **Solo códigos HTTP, sin cuerpo:** no distinguen casos con el mismo status, como un 401 por credenciales inválidas y otro por token vencido.

## Consecuencias

- Un único formato de error en toda la API, incluidos los 401 y 403.
- Agregar un error nuevo es sumar un `type` y su mapeo en `GlobalExceptionHandler`.
- Los mensajes de `title` y `detail` están en inglés con locale fijo, así que no dependen del idioma del servidor ni del cliente.
- GraphQL (Fase 5) usa su propio formato de errores, pero con los mismos códigos de negocio.
