# ADR-004: JWT stateless con OAuth2 Resource Server nativo

## Estado

Aceptado

## Contexto

La API necesita un login seguro, y autenticación y autorización para acceder al catálogo. No tiene frontend propio: la consumen clientes HTTP (curl, Swagger UI, GraphiQL, clientes MCP).

## Decisión

- `POST /api/v1/auth/login` valida las credenciales con `AuthenticationManager` + `DaoAuthenticationProvider` + BCrypt y emite un JWT HS256:
  - claims `iss`, `sub`, `iat`, `exp` (1 h) y `scope: catalog:read`
  - firmado con `NimbusJwtEncoder`
- El resto de la API valida el token con `oauth2ResourceServer().jwt()`: firma, expiración e issuer.
- Autorización explícita: los endpoints del catálogo exigen la authority `SCOPE_catalog:read`, no solo estar autenticado.
- Sesión `STATELESS` y CSRF deshabilitado: no hay cookies de sesión, el token viaja en el header `Authorization`.
- 401 y 403 devuelven `ProblemDetail`, igual que el resto de los errores (ADR-013).

## Alternativas descartadas

- **Filtro JWT escrito a mano:** más código de seguridad propio para mantener y auditar.
- **Sesiones con cookie:** exige CSRF, ata al cliente a un navegador y no escala horizontalmente sin sesión compartida.
- **RS256 con par de claves:** útil cuando otro servicio valida los tokens. Acá emite y valida la misma app.

## Consecuencias

- Muy poco código de seguridad propio. La validación es la estándar de Spring Security.
- El mismo token sirve para REST, GraphQL y MCP.
- No hay revocación de tokens. Se mitiga con una expiración corta (1 h); los refresh tokens quedan fuera de alcance.
- Migrar a un Identity Provider externo (Keycloak, Auth0) es cambiar el `JwtDecoder` por `issuer-uri`.
