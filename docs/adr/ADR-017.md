# ADR-017: Swagger UI y GraphiQL públicos en producción

## Estado

Aceptado

## Contexto

Quien revisa la API tiene que poder probarla en la URL de Render sin clonar el repo ni instalar nada: llamar a los endpoints REST y escribir queries GraphQL desde el navegador. Swagger UI y GraphiQL suelen tratarse como herramientas de desarrollo y se deshabilitan en producción.

## Decisión

- Swagger UI (`/swagger-ui.html`, `/v3/api-docs`) y GraphiQL (`/graphiql`) están habilitados en todos los perfiles, incluido `prod`.
- Las dos páginas cargan sin token. Los datos siguen protegidos: `/api/v1/**` y `/graphql` exigen el JWT con el scope `catalog:read`.
- En Swagger UI el token se pega en **Authorize**. En GraphiQL va en el panel de headers: `{"Authorization": "Bearer <token>"}`.
- El token se obtiene con `POST /api/v1/auth/login` y el usuario demo, que se puede llamar desde el mismo Swagger UI.

## Alternativas descartadas

- **Interfaces solo en local:** obliga a clonar el repo o a armar las llamadas con curl.
- **Interfaces públicas sin JWT:** expone el catálogo sin autenticación y deja de demostrar la seguridad de la API.

## Consecuencias

- REST y GraphQL se prueban desde el navegador, sobre la URL de Render.
- El esquema de la API (OpenAPI e introspección de GraphQL) queda público: nombres de recursos y campos de un catálogo público, sin datos de usuarios.
- `SecurityConfig` suma estas rutas a las públicas. Los tests verifican que las páginas cargan sin token y que los datos devuelven 401 sin él.
