# ADR-016: GraphQL y MCP como adaptadores del mismo `CatalogService`

## Estado

Aceptado

## Contexto

Además de REST, el catálogo se expone por GraphQL (consultas con la forma que pide el cliente) y como servidor MCP (para que clientes de IA como Claude o Cursor consulten el catálogo con tools). Las dos interfaces necesitan la misma paginación, los mismos filtros, la misma caché, la misma resiliencia y la misma seguridad que REST.

## Decisión

- GraphQL (Spring for GraphQL, `/graphql`) y MCP (Spring AI, transporte HTTP streamable en `/mcp`) son adaptadores en `catalog/graphql` y `catalog/mcp`, hermanos de `catalog/api`.
- Todos delegan en `CatalogService`: ninguno tiene lógica de negocio propia.
- Se despliegan en el mismo jar y el mismo servicio de Render, con el mismo JWT y el scope `catalog:read`.
- La métrica `catalog.queries` suma el tag `channel` (`rest`, `graphql`, `mcp`).
- El servidor MCP no llama a ningún modelo: solo expone tools. El modelo lo pone el cliente, así que no hace falta API key.

## Alternativas descartadas

- **Un servicio separado por protocolo:** duplica deploy, configuración de seguridad y caché, y obliga a llamadas entre servicios.
- **Un gateway GraphQL aparte delante de la API REST:** suma un salto de red y otra pieza para desplegar.

## Consecuencias

- Sin lógica duplicada: un cambio en la paginación o en los filtros aplica a los tres canales.
- Una sola configuración de seguridad y un solo deploy.
- El arranque es algo más lento en el plan free por las dependencias nuevas; se mide y se anota en el README.
