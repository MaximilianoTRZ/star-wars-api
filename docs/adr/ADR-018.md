# ADR-018: Estrategia de logging para producción

## Estado

Aceptado

## Contexto

Desde la Fase 3 los logs llevan un `requestId` y en `prod` salen en JSON ECS, pero casi no había eventos. En Render apareció un `WARN SWAPI did not respond for people: HTTP connect timed out` y la request respondió 200 en ~9 s: el retry la había recuperado, pero el log no lo mostraba. Tampoco había una línea por request, ni eventos de login, ni cambios del circuit breaker.

Los logs se leen en la consola de Render, que tiene retención corta y solo permite buscar por texto.

## Decisión

**Niveles**

| Nivel | Cuándo |
| --- | --- |
| `ERROR` | Fallo nuestro que requiere acción (excepción no controlada, con stack trace) |
| `WARN` | Degradación o fallo externo: retries agotados, circuito abierto, respuesta 5xx, login fallido o bloqueado |
| `INFO` | Eventos de negocio y de ciclo de vida: línea de acceso, retry que se recupera, login exitoso, 401/403 |
| `DEBUG` | Diagnóstico, apagado en `prod`: cada intento fallido contra SWAPI |

**Reglas**

- Un evento se loguea una vez, donde se decide. Un intento fallido contra SWAPI es `DEBUG`; el retry, el éxito tras reintentar o el fallo final lo loguea `SwapiResilienceLogging`, suscripto a los eventos de Resilience4j.
- Mensaje legible más key-values de SLF4J (`addKeyValue`). En `prod` se vuelven campos del JSON (`http.status`, `swapi.reason`, `client.ip`); en local se leen en el mensaje.
- Una línea de acceso por request (`RequestLoggingFilter`): método, ruta (el patrón, no el valor), status, duración y usuario. Sin query string. `/livez`, `/readyz` y `/actuator/**` no se loguean. Los 4xx esperados no se loguean como error: alcanza con esta línea.
- MDC: `requestId` (`CorrelationIdFilter`) y `user` (`AuthenticatedUserFilter`, solo el `sub` del token).
- Nunca se loguean contraseñas, tokens, el header `Authorization` ni el body del login. Un login fallido se loguea con la IP y sin username, porque ese campo puede contener una contraseña mal tipeada.
- ECS con `service.environment` y `service.node.name` (`RENDER_INSTANCE_ID`), y stack traces con la causa raíz primero y tamaño acotado.
- El nivel se cambia con una variable de entorno (`LOGGING_LEVEL_DEV_STARWARS=DEBUG`) y un reinicio. `/actuator/loggers` no se expone: en `prod` comparte el puerto público.

## Alternativas descartadas

- **Enviar los logs a Grafana Cloud Loki:** permitiría buscar por campo y sumar un panel de logs al dashboard, pero agrega un appender o un log stream y otra credencial. Queda como siguiente paso: Render puede reenviar los logs por syslog a un colector, sin cambios en la app.
- **Access log de Tomcat:** no lleva el MDC ni sale en ECS, y no conoce el patrón de la ruta.
- **Loguear cada intento fallido en `WARN`** (lo que había): un fallo recuperado parece un error, y un fallo final aparece tres veces.
- **`/actuator/loggers` en `prod`:** cambiar niveles sin reiniciar no justifica exponer un endpoint de escritura en el puerto público.

## Consecuencias

- Un retry recuperado se lee como tal: `SWAPI attempt 1/3 failed (CONNECTION), retrying in 200ms`, `SWAPI call succeeded on attempt 2` y la línea de acceso con el 200, todo con el mismo `requestId`.
- Cada request agrega una línea `INFO`. Con el tráfico de la demo no es un problema; con mucho tráfico se podría muestrear o bajar a `DEBUG` para las rutas exitosas.
- Hay tests que verifican los mensajes y que los secretos no aparecen en la salida, así que cambiar un mensaje implica tocar esos tests.
